# Процесс работы

Два уровня: лёгкая спецификация на веху, план и реализация на каждый шаг.

## Документы

| Файл | Отвечает на вопрос | Меняется |
| --- | --- | --- |
| `docs/design.md` | какая игра | редко |
| `docs/roadmap.md` | в каком порядке | после каждого шага |
| `docs/decisions.md` | почему так решили | при новом решении |
| `docs/ideas.md` | что отложено | когда приходит идея |
| `docs/stages/NN-имя/spec.md` | что делаем в вехе | до начала вехи |
| `docs/stages/NN-имя/N.M-имя.md` | как делаем шаг | один раз, потом не трогается |

Живые документы: первые четыре и комментарии в начале модулей. Файлы шагов
это журнал: закрытый файл шага больше не редактируется.

## Веха

1. Автор и агент пишут `spec.md`: что должно заработать, что не делаем,
   ключевые решения по структурам данных, критерии готовности. Одна страница.
2. Шаги в `roadmap.md` уточняются по спецификации.
3. Автор утверждает спецификацию.

## Шаг

1. **Постановка.** Автор называет шаг. Агент читает правила, спецификацию
   вехи, файл предыдущего шага и нужный код.
2. **План.** Агент создаёт `docs/stages/NN-имя/N.M-имя.md` по шаблону
   `docs/stages/_template.md` и заполняет «Цель», «План», «Тесты».
   Кода нет. Агент останавливается.
3. **Утверждение.** Автор читает план, спрашивает, правит, подтверждает.
4. **Тесты.** Для симуляции сначала пишутся тесты, которые не проходят.
5. **Реализация.** Минимальный код, чтобы тесты прошли.
6. **Проверки.** `cargo fmt`, `cargo clippy`, `cargo test`. Позже к ним
   добавится тест детерминизма.
7. **Итог.** Агент заполняет «Итог», «Новое в Rust», «Открытые вопросы».
8. **Ревью.** Автор читает diff, задаёт вопросы, запускает игру.
9. **Закрытие.** Отметка в `roadmap.md`, коммит по просьбе автора,
   при необходимости строка в `decisions.md`.

Файл шага не длиннее 40 строк. Для мелких правок (опечатка, переименование,
настройка линтера) файл шага не нужен.

## Отступления от схемы

- **Клиент и графика.** Тесты вперёд не пишутся. В плане указывается,
  что автор должен увидеть на экране.
- **Неясные задачи.** Сначала черновой эксперимент в отдельной ветке
  на выброс, потом спецификация и чистая реализация.
- **Баги.** Сначала воспроизведение: реплей или падающий тест. Потом
  исправление.

## Выбор модели

Модель сессии выбирает автор. Агент подсказывает: в разделе «План» есть
строка «Рекомендуемая модель» с причиной, в «Итоге» строка «Выполнено
на модели».

- **Старшая:** спецификации вех, архитектура, фиксированная точка,
  идентификаторы, `step()`, хеш, поиск пути, избегание, броня,
  расхождение хешей, любые изменения структуры данных мира.
- **Средняя:** реализация по утверждённому плану, тесты, клиент,
  интерфейс, файлы данных.
- **Лёгкая:** переименования, комментарии, обновление документов, поиск.

Вехи 1 и 2 выполняются на старшей модели целиком.

Если задача не решена за две попытки, агент останавливается, записывает
в файл шага, что пробовал, и предлагает новую сессию на старшей модели.

## Сессии

- Новая сессия на каждый шаг. Длинные сессии хуже соблюдают правила
  и дороже.
- Перед сессией рабочее дерево git чистое, шаг делается в отдельной ветке.

## Что добавляется позже

Добавляется только под конкретную повторяющуюся проблему.

- Независимый ревьюер с чистым контекстом: примерно с вехи 6.
- Вспомогательный агент для поиска по коду и документации.
- Собственные скилы: когда одно и то же объясняется в третий раз.
- Образцовый модуль: после вехи 2 выбрать файл, на который можно
  ссылаться словами «делай как здесь».
