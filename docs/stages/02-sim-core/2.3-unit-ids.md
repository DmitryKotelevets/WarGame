# 2.3 Идентификаторы с поколением и хранилище юнитов

## Цель

В `crates/sim` есть `UnitId` и хранилище `UnitStore`: юнит можно создать, найти по идентификатору, обойти всех по порядку и удалить в конце тика. Идентификатор погибшего юнита никогда не укажет на нового, занявшего ту же ячейку.

## План

- Новый `crates/sim/src/unit.rs`: `pub struct UnitId { pub index: u32, pub generation: u32 }` (`Clone, Copy, PartialEq, Eq, Debug`) и `pub struct Unit { pub id: UnitId, pub position: Vec2Fixed }`. Других полей у юнита пока нет: скорость и цель появятся в 2.8.
- Новый `crates/sim/src/unit_store.rs`: `pub struct UnitStore { slots: Vec<Slot> }`, поле закрыто. `Slot { generation: u32, unit: Option<Unit>, marked_for_removal: bool }`. `index` в `UnitId` это номер ячейки в `slots`.
- `spawn(position) -> UnitId`: занимает **свободную ячейку с наименьшим индексом** (простой проход по `slots`), если свободных нет, добавляет новую. Отдельного списка свободных ячеек нет: тогда порядок в нём был бы скрытым состоянием, которое влияет на будущие идентификаторы и которое пришлось бы хешировать и сохранять. Проход по 300 ячейкам ничего не стоит.
- `get(id) -> Option<&Unit>`, `get_mut(id) -> Option<&mut Unit>`: `None`, если индекс за пределами, ячейка пуста или поколение не совпало. Устаревший идентификатор это обычная ситуация (цель погибла), поэтому `Option`, а не паника.
- `mark_for_removal(id)`: только ставит отметку, юнит остаётся виден до конца тика. Повторная отметка допустима (двое убили одного за тик). Отметка по устаревшему идентификатору это паника: вызывающий код обязан был сначала найти юнит.
- `remove_marked()`: освобождает отмеченные ячейки и увеличивает их поколение на 1. Вызывать её в конце тика будет `step()` из шага 2.4. Переполнение поколения (4 млрд смертей в одной ячейке) это паника, как переполнение в `Fixed`.
- `iter()`, `iter_mut()`: живые юниты по возрастанию индекса, включая отмеченных на удаление. `len()`: число живых.
- `lib.rs`: `pub mod unit;`, `pub mod unit_store;`. Новых крейтов нет. `SIM_VERSION` не меняется: логики, влияющей на реплеи, ещё нет.
- Рекомендуемая модель: старшая (идентификаторы, веха 2 целиком на ней).
- Риски: `Unit.id` дублирует номер ячейки; рассогласование ловят тесты здесь и проверка инвариантов в 2.9.
- Альтернативы:
  - Список свободных ячеек (стек): `spawn` за O(1), но лишнее состояние (см. выше). Вернуться, если замер в 6.7 покажет проблему.
  - Обобщённое хранилище `Store<T>` сразу для снарядов и зданий: дженерик до третьего повторения, против правил стиля.
  - Юнит без поля `id`, обход отдаёт пары `(UnitId, &Unit)`: нет дублирования, но системам неудобнее.
  - Закрытые поля `UnitId` с конструктором: подделанный идентификатор и так безвреден (`get` вернёт `None`), а хешу и реплею поля нужны.

## Тесты

Сначала тесты, потом реализация.

1. `spawn` → `get` возвращает юнит с той же позицией и тем же `id`; первые два юнита получают индексы 0 и 1, поколение 0; `len` растёт.
2. `get` → `None` для индекса за пределами, для чужого поколения, для пустого хранилища.
3. `get_mut`: изменённая позиция видна через `get`.
4. После `mark_for_removal` юнит ещё доступен и входит в `iter` и `len`; после `remove_marked` его нет.
5. Ячейка используется заново: тот же индекс, поколение на 1 больше; старый идентификатор даёт `None`, новый работает.
6. Создать 3, удалить индексы 2 и 0, создать ещё 3: индексы 0, 2, 3.
7. `iter` идёт по возрастанию индекса после удалений и повторного заполнения.
8. Повторная отметка одного юнита не ломает удаление; отметка по устаревшему идентификатору паникует; переполнение поколения паникует.
9. `proptest`: случайная последовательность «создать / отметить / удалить отмеченных» сверяется с простой моделью (список живых): каждый живой находится, каждый удалённый даёт `None` навсегда, `iter` по возрастанию, `len` совпадает. Та же последовательность дважды даёт одинаковые идентификаторы.

## Итог

Сделано по плану. Отличия:

- Добавлен `is_empty()` и `#[derive(Default)]` для `UnitStore`: clippy требует их рядом с `len()` и `new()` без аргументов.
- Тестов больше, чем в списке: `remove_marked` без отметок ничего не меняет, `iter_mut` меняет каждого, отметка по индексу за пределами паникует.
- Выполнено на модели: старшая (Claude Fable 5.2).
- Тесты до реализации: `cargo test -p sim` не собирался, `cannot find type UnitStore` (18 раз).
- Вывод проверок (`scripts/check.sh`, код возврата 0): `== 1/3 Форматирование` без замечаний; `== 2/3 Clippy` без предупреждений; `== 3/3 Тесты`: в `sim` `test result: ok. 47 passed; 0 failed` (15 новых, все в `unit_store::tests`), в `client` `2 passed`; `== Все проверки прошли`.

## Новое в Rust

- `&mut self`: метод меняет значение, у которого вызван. Пока жива ссылка, полученная из `get_mut`, хранилище нельзя трогать иначе: это и есть проверка заимствований.
- `Option<&Unit>`: ссылка на юнит внутри хранилища либо ничего. `option.as_ref()` превращает `&Option<Unit>` в `Option<&Unit>`, `as_mut()` то же для изменяемой ссылки.
- `let slot = self.slots.get(i)?;`: знак `?` на `Option`. Если там `None`, функция сразу возвращает `None`, иначе достаёт значение. Короткая запись `match` с ранним выходом.
- `vec.get(i)` против `vec[i]`: первое возвращает `Option` и не падает на плохом индексе, второе паникует.
- `for (index, slot) in self.slots.iter().enumerate()`: обход с номером элемента; `(index, slot)` разбирает пару на две переменные. `break` прерывает цикл, `continue` переходит к следующему элементу.
- `-> impl Iterator<Item = &Unit>`: функция возвращает «что-то, что можно обойти в `for`, выдающее `&Unit`», не называя точный тип.
- `.filter_map(|slot| slot.unit.as_ref())`: `|slot| ...` это замыкание, безымянная функция от `slot`. `filter_map` вызывает её для каждого элемента, выбрасывает `None` и разворачивает `Some`.
- `panic!("... {id:?}")`: имя переменной прямо в фигурных скобках, `:?` печатает через `Debug`.
- В тестах: `vec.retain(|x| условие)` оставляет только подходящие элементы; `slice.windows(2)` выдаёт все пары соседей; `impl Strategy<Value = T>` это описание того, как `proptest` подбирает случайное `T`.

## Открытые вопросы

- `unit_store.rs` 471 строка при лимите 400, из них 307 это тесты. Предлагаю отдельным шагом решить общее правило: считать лимит без тестов или выносить тесты в соседний файл. Сам не делил.
- `spawn` принимает только позицию. С ростом числа полей юнита (2.8, 7.2) сигнатуру придётся менять.
- `len()` и поиск свободной ячейки это проход по всем ячейкам. Скорость не измерялась, вернуться в 6.7.
- Хранилище никогда не сжимается: число ячеек равно максимуму одновременно живших юнитов.
- `remove_marked` не сообщает, кого удалил. События гибели появятся в 7.7.
- `Unit.id` и номер ячейки могут разойтись, только если код внутри модуля ошибётся; проверка инварианта это шаг 2.9.
- `get_mut` и `iter_mut` позволяют переписать `unit.id` снаружи. Поле открыто для простоты; запрет это тоже 2.9 или закрытое поле.
- Спецификация вехи 2 всё ещё не утверждена автором.
