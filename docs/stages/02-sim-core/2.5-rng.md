# 2.5 Детерминированный генератор случайных чисел

## Цель

В `crates/sim` есть генератор `Rng`: один и тот же сид даёт одну и ту же последовательность чисел на любой платформе. Его состояние лежит в `World`, мир создаётся с сидом.

## План

- Новый `crates/sim/src/rng.rs`: `pub struct Rng { state: u64 }` (`Clone, Copy, PartialEq, Eq, Debug`), поле закрыто.
- **Алгоритм (нужно решение автора): SplitMix64.** Всё состояние это одно число `u64`. Шаг: прибавить константу, затем три раза перемешать сдвигами и умножениями; около 8 строк. Алгоритм открытый (общественное достояние, автор Себастьяно Винья), используется в стандартной библиотеке Java. Подходит любой сид, включая 0. Период 2^64: при тысяче чисел за тик не повторится за миллионы лет.
- Арифметика через `wrapping_add` и `wrapping_mul`: здесь переполнение это часть алгоритма, а не ошибка, в отличие от `Fixed`. Результат одинаков в отладочной и выпускной сборке и на всех процессорах.
- `Rng::new(seed: u64)`, `next_u64()`, `next_u32()` (старшие 32 бита от `next_u64`).
- `next_below(bound: u32) -> u32`: число от 0 до `bound - 1`. Считается как `(next_u32 * bound) >> 32` в `u64`. `bound == 0` это паника. Каждый вызов тратит ровно одно число генератора.
- `state() -> u64`: для хеша мира в 2.6. Обратного `from_state` нет, пока нет сохранений.
- `world.rs`: поле `pub rng: Rng`, `World::new()` становится `World::new(seed: u64)`. `#[derive(Default)]` у `World` убирается: мира без сида быть не должно.
- **Правка существующих тестов (нужно согласие):** в 6 тестах из шага 2.4 (`world.rs`, `step.rs`) `World::new()` заменяется на `World::new(0)`. Проверки в них не меняются.
- `step()` не меняется: генератор пока никто не вызывает. `lib.rs`: `pub mod rng;`. Новых крейтов нет. `SIM_VERSION` не меняется.
- Рекомендуемая модель: старшая (веха 2 целиком на ней).
- Риски:
  - Ошибка в константе даст рабочий, но другой генератор. Защита: тест на эталонные числа. Я сверил их двумя способами: по памяти из опубликованных примеров и расчётом по описанию алгоритма в Python; оба совпали.
  - `next_below` даёт небольшой перекос: при `bound`, не являющемся степенью двойки, часть значений выпадает чаще на долю порядка `bound / 2^32`. Для разброса и выбора цели это незаметно.
- Альтернативы:
  - PCG32: статистически лучше, но состояние из двух чисел и более длинное объяснение. Для игры разницы нет.
  - Xorshift64: ещё короче, но сид 0 ломает его навсегда (выдаёт только нули).
  - `next_below` с отбраковкой (точно равномерный): тратит непредсказуемое число вызовов генератора и требует цикла.
  - Крейт `rand`: алгоритм по умолчанию не обещан одинаковым между версиями, это ломает реплеи.

## Тесты

Сначала тесты, потом реализация.

1. Эталон: сид 0 даёт `0xe220a8397b1dcdaf`, `0x6e789e6aa1b965f4`, `0x06c45d188009454f`; сид 1234567 даёт `6457827717110365317`, `3203168211198807973`, `9817491932198370423`.
2. Два генератора с одним сидом выдают одинаковые 1000 чисел; с разными сидами первые числа различаются.
3. Копия генератора продолжает ту же последовательность, что и оригинал; `state()` у них совпадает и меняется после `next_u64`.
4. `next_u32` это старшие 32 бита того же `next_u64`.
5. `next_below(1)` всегда 0; `next_below(6)` за 10 000 вызовов выдаёт каждое из шести значений, и каждое от 1500 до 1850 раз; `next_below(0)` паникует.
6. `proptest`: для любых сида и `bound >= 1` результат `next_below` меньше `bound`.
7. `World::new(seed)`: генератор мира равен `Rng::new(seed)`; `step()` состояние генератора не меняет.

## Итог

Сделано по плану, алгоритм SplitMix64. Отличий в коде нет. В существующих тестах шага 2.4 `World::new()` заменён на `World::new(0)` в 6 местах, проверки не тронуты.

- Выполнено на модели: старшая (Claude Fable 5.2).
- Тесты до реализации: `cargo test -p sim` не собирался: `no field rng on type World` (5 раз), `this function takes 0 arguments but 1 argument was supplied` (9 раз), `Rng` не найден.
- Одна заминка: в тестах `rng.rs` имя `Rng` из `use super::*` столкнулось с `Rng` из `proptest::prelude::*`. Исправлено явным `use super::Rng;`.
- Вывод проверок (`scripts/check.sh`, код возврата 0): `== 1/3 Форматирование` без замечаний; `== 2/3 Clippy` без предупреждений; `== 3/3 Тесты`: в `sim` `test result: ok. 67 passed; 0 failed` (11 новых: 9 в `rng::tests`, 1 в `world::tests`, 1 в `step::tests`), в `client` `2 passed`; `== Все проверки прошли`.
- Размеры файлов: `rng.rs` 195 строк, `world.rs` 60, `step.rs` 109.

## Новое в Rust

- `a.wrapping_add(b)`, `a.wrapping_mul(b)`: арифметика, которая при переполнении отбрасывает старшие биты и не паникует. Обычные `+` и `*` в отладочной сборке паникуют, в выпускной заворачиваются молча; явный метод ведёт себя одинаково везде.
- `x ^ y`: побитовое «исключающее или». `x >> 30`: сдвиг битов вправо, то же, что деление на 2^30 с отбрасыванием остатка.
- `const INCREMENT: u64 = 0x9e37_79b9_7f4a_7c15;`: константа модуля. `0x` это запись в шестнадцатеричной системе, подчёркивания только для читаемости.
- `let mut mixed = ...; mixed = ...;`: переменная, объявленная с `mut`, может получать новое значение.
- `[0u32; 6]`: массив из шести нулей типа `u32`. Размер массива это часть типа и известен при компиляции, в отличие от `Vec`.
- `(1500..=1850).contains(&count)`: диапазон с включённым правым краем и проверка, что число в него попадает.
- `assert!(условие, "текст {x:?}")`: при провале проверки печатается свой текст.
- `1u32..` в `proptest`: диапазон без верхней границы, «любое `u32` от 1».
- `use super::Rng;` против `use super::*;`: явно названное имя сильнее имени, пришедшего через звёздочку. Так разрешается столкновение двух одинаковых имён.

## Открытые вопросы

- Генератор никто не вызывает: первый потребитель появится в вехе 7 (выбор цели вразнобой) или 8 (разброс).
- `next_below` даёт перекос порядка `bound / 2^32`. Если где-то понадобится точная равномерность, нужна отбраковка.
- Нет случайного `Fixed` (например, от 0 до 1) и случайного числа в диапазоне `от..до`. Добавляются, когда понадобятся.
- Нет `Rng::from_state`: восстановить генератор из сохранённого состояния пока нельзя. Понадобится для сохранений (после 1.0).
- Один генератор на весь мир: лишний вызов в любой системе сдвигает случайность для всех остальных. Для lockstep это нормально, но при отладке расхождений полезно помнить.
- Статистическое качество не проверялось своими тестами: проверено только совпадение с эталонными числами и грубая равномерность `next_below(6)`.
- Откуда берётся сид (сценарий, часы на стороне клиента), решают шаги 2.10 и 2.13. Сейчас его передаёт вызывающий код.
- Спецификация вехи 2 всё ещё не утверждена автором.
