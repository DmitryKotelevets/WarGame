# 1.4 CI

## Цель

При каждом push в `master` и в каждом pull request GitHub Actions запускает `scripts/check.sh` на macOS, Windows и Linux. Отдельная проверка не пропускает `todo!` в коде.

## План

План переписан 2026-11-27: первый вариант был составлен до Bevy и до появления `origin`, утверждён не был.

- Новый `.github/workflows/ci.yml`. Запуск: push в `master`, любой pull request, ручной запуск кнопкой (`workflow_dispatch`). Права токена только на чтение (`permissions: contents: read`). Новый push в ту же ветку отменяет предыдущий запуск (`concurrency`). Две задачи (job):
  - `check`: матрица `ubuntu-latest`, `macos-latest`, `windows-latest`, `fail-fast: false` (падение на одной системе не отменяет остальные, видно всю картину). Шаги: `actions/checkout@v7`; на Linux системные библиотеки для Bevy; установка Rust через `rustup toolchain install` (версию и компоненты берёт из `rust-toolchain.toml`, rustup уже есть на раннерах); кеш; `scripts/check.sh` с `shell: bash` (на Windows это Git Bash).
  - `no-todo`: только Linux, запускает `scripts/check-todo.sh`.
- Библиотеки Linux взяты из `docs/linux_dependencies.md` в исходниках Bevy 0.20.1: `g++ pkg-config libx11-dev libasound2-dev libudev-dev libxkbcommon-x11-0 libwayland-dev libxkbcommon-dev`. Wayland нужен, потому что включён в Bevy по умолчанию.
- В CI отладочная информация выключена (`CARGO_PROFILE_DEV_DEBUG=0` и то же для `TEST` в переменных окружения workflow): сборка Bevy быстрее, папка `target` и кеш в несколько раз меньше. Локальная сборка не меняется.
- Новый `scripts/check-todo.sh`: `grep -rn` по `crates/` в файлах `*.rs` ищет `todo!` и `unimplemented!`; нашёл → печатает строки и код возврата 1. В `check.sh` не входит: во время работы над шагом `todo!` разрешён, в `master` нет.
- Новый `.gitattributes`: `* text=auto eol=lf`. Без него git на Windows отдаёт `check.sh` с переводами строк CRLF, и bash на нём падает.
- Кеш сборки: `Swatinem/rust-cache@v2` (сторонний action, фактический стандарт для Rust: около 2000 звёзд, последний выпуск v2.9.3 в октябре 2026; сам строит ключ из `Cargo.lock` и версии компилятора). **Нужно согласие**, это внешняя зависимость. Лицензия LGPL-3.0 нас не касается: action работает в CI как инструмент, в код игры не попадает.
- `README.md`: строка про CI и `check-todo.sh`; устаревший раздел «Перед первой сессией» не трогаю. Код Rust не меняется.
- Рекомендуемая модель: старшая (веха 1 целиком на ней); по сложности хватило бы средней.
- Риски:
  - Workflow нельзя запустить локально. Проверка настоящая только после push; первый запуск, скорее всего, потребует одной-двух правок (особенно Windows и Linux, где проект ещё ни разу не собирался).
  - Первая сборка Bevy на раннере займёт 10-20 минут на каждой системе. Дальше спасает кеш, но у GitHub лимит 10 ГБ кеша на репозиторий: три системы с Bevy могут в него не уложиться, тогда старые кеши вытесняются.
  - `rust-toolchain.toml` задаёт `stable` без номера: CI возьмёт самый свежий Rust, и новый clippy может однажды покраснеть без изменений в коде. Закрепить точную версию это отдельное решение.
  - Тесты `sim` с `proptest` на каждой системе берут свои случайные числа: редкий провал на одной платформе возможен и будет настоящей находкой.
  - Репозиторий публичный, минуты Actions бесплатны.
- Альтернативы:
  - `todo!` ловить линтом `clippy::todo` в `[workspace.lints]` вместо grep: точнее (не срабатывает на комментарии и строки), но тогда `check.sh` падает и во время работы, а спецификация просит отдельную проверку.
  - Кеш на `actions/cache` с ключом вручную: без стороннего action, но 10-15 строк YAML, которые легко написать неправильно.
  - Проверять `client` только на одной системе, а на трёх только `sim`: в разы быстрее, но критерий вехи это сборка всего проекта на трёх системах.

## Тесты

Автотестов нет. Локально:

1. `check-todo.sh` на чистом проекте: код 0.
2. На копии проекта во временной папке добавлен `todo!()` в `crates/sim/src/lib.rs`: код 1, в выводе файл и номер строки.
3. Там же `unimplemented!()`: код 1.
4. Запуск из `crates/sim`: работает.
5. `scripts/check.sh` на рабочем проекте проходит.
6. `ci.yml` разбирается как корректный YAML.

После push ветки и открытия pull request (push по просьбе автора):

7. Обе задачи зелёные, `check` на трёх системах.
8. Повторный запуск: в логе видно, что кеш восстановлен, сборка заметно быстрее.
9. Проверку «ветка с `todo!` красная» на GitHub не делаю: её заменяют пункты 2 и 3.

## Новое в Rust

Кода Rust в шаге нет. Новое в инструментах:

- Workflow GitHub Actions это YAML-файл в `.github/workflows`: `on` говорит, когда запускать, `jobs` это независимые задачи на отдельных машинах, `steps` это команды внутри задачи по порядку.
- `strategy.matrix`: одна задача размножается по списку значений, здесь по трём системам.
- `uses: имя@версия` подключает готовое действие, `run:` выполняет команду оболочки.
- `rustup toolchain install` без аргументов ставит то, что записано в `rust-toolchain.toml`.
- `.gitattributes` с `eol=lf`: git не подменяет переводы строк на Windows.

## Открытые вопросы

- Клиент на Windows и Linux только собирается и проходит тесты. Окно там не открывалось: у раннеров нет экрана.
- Динамическая линковка (`--features dynamic_linking`) в CI не проверяется.
- `rust-toolchain.toml` задаёт `stable` без номера: новый выпуск Rust может сломать CI без изменений в коде.
- Версии действий заданы тегами (`@v7`, `@v2`), а не хешами коммитов: обновление внутри тега приходит само.
- `check-todo.sh` срабатывает и на `todo!` в комментарии или строке.
- Защита ветки `master` (запрет слияния при красном CI) в настройках GitHub не включена: это делает автор.
- Раздел «Перед первой сессией» в `README.md` устарел, не трогал.
