# Правила проекта

RTS на Rust. Автор проекта хочет понимать весь код, поэтому понятность
важнее скорости и краткости.

В начале каждой сессии прочитай:

1. `docs/process.md`: порядок работы над шагом
2. `docs/roadmap.md`: где мы сейчас
3. `docs/stages/<текущая веха>/spec.md`: что делаем в этой вехе

По необходимости: `docs/design.md` (какая игра), `docs/decisions.md`
(почему так решили).

## Структура

- `crates/sim`: детерминированное ядро. Не зависит от Bevy и от других
  крейтов проекта.
- `crates/client`: Bevy, рендер, ввод, звук, интерфейс. Только читает
  состояние и события симуляции. Изменения мира идут через команды.
- `crates/tools`: запуск без окна, позже MCP-сервер.

Зависимости направлены в одну сторону: `client` и `tools` зависят от `sim`,
обратное запрещено.

## Команды

```sh
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test --workspace
```

Шаг не закрыт, пока все три не проходят. Итоговая проверка одной командой:
`scripts/check.sh` (то же самое, но форматирование только проверяется).

## Правила симуляции (`crates/sim`)

- Никаких `f32`/`f64` в логике. Только числа с фиксированной точкой.
- Не обходи `HashMap`/`HashSet`: порядок не определён. Используй `Vec`
  или `BTreeMap`.
- Случайность только через генератор с сидом из состояния мира.
- Никакого системного времени, файлов, потоков, сети.
- Порядок систем в `step()` задан явным списком в одном месте.
- Юниты удаляются в конце тика, а не посреди обработки.
- В `match` по своим перечислениям перечисляй все варианты, без `_`.
- Не используй тихие запасные значения (`unwrap_or_default` и подобное),
  которые прячут ошибку. В отладочной сборке лучше упасть.

## Стиль кода

- Простой прямолинейный код, даже если он длиннее. Обычные структуры
  и функции. Трейты, дженерики и макросы только при явной необходимости.
- Абстракция появляется после третьего повторения, не раньше.
- В начале каждого файла комментарий `//!`: что делает модуль и почему так.
- Комментарии на русском, объясняют «почему». Идентификаторы на английском.
- Отдельные типы для разных сущностей (`UnitId`, `Tick`, `Fixed`).
- Не обходи проверку заимствований через `clone()` или `Rc<RefCell<..>>`
  без объяснения причины.
- Перед новой вспомогательной функцией поищи существующую.
- Файлы небольшие. Если файл перерос 400 строк, предложи разделить.

## Порядок работы

Подробно в `docs/process.md`. Главное:

1. Создай файл шага по шаблону, заполни «Цель», «План», «Тесты».
   **Код не пиши. Остановись и жди подтверждения.**
2. После подтверждения: сначала тесты, потом реализация.
3. Запусти проверки, заполни «Итог», отметь шаг в роадмапе.

Один шаг это одна задача и небольшой diff. Не рефактори соседний код
«заодно»: предложи это отдельным шагом.

## Честность результата

- Существующие тесты и эталонные хеши не меняй без согласия.
- В «Итоге» приведи фактический вывод команд проверки.
- Все заглушки и упрощения перечисли в «Открытых вопросах».
- Если задача не решена за две попытки, остановись и опиши, что пробовал.
- Возражай, если считаешь решение автора неудачным.

## Зависимости

- Новый крейт только с согласия автора. Перед предложением убедись,
  что он существует и им пользуются.
- Версии Bevy и ключевых крейтов зафиксированы. Обновление это
  отдельный шаг.
- API Bevy сверяй с документацией используемой версии, не пиши по памяти.
- Не переноси код из источников под GPL (включая исходники Generals).

## Безопасность репозитория

- Не выполняй команды, удаляющие файлы или историю git.
- Не делай коммиты и push без просьбы.

## Объяснения

Каждую конструкцию Rust, которая встречается в проекте впервые, объясни
одним-двумя предложениями в разделе «Новое в Rust» файла шага.
